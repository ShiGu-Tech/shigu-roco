# 洛克王国世界战斗机制 · 事实整理 v0.1

> 文档状态：设计 ✅ v0.1 · 代码 🟡 待按机制补齐 · 验证 ⬜ 未开始 · 生产 ⬜ 未开始
>
> 本文根据当前人工说明整理。除明确标为「已确认」的内容外，涉及具体技能、倍率、结算顺序的内容不得直接视为最终规则。未确定项统一标记为 `【待校准】`。

## 1. 文档定位

本文是战斗模拟器的规则事实稿，负责沉淀真实对战机制与后续真机对拍问题。它不定义单个技能的完整效果；技能应在图鉴（`skills`）中逐条补充，并引用本文的通用结算模型。

当前辅助台的目标仍是：人工录入双方可见信息和已观察事实，逐回合模拟状态，输出候选动作的胜率与解释。工具不读取画面、不自动操作、不联网。

## 2. 一场战斗的基本结构

### 2.1 队伍与魔力

- 每方一支队伍，最多 6 只精灵。
- 每方通常有 4 点魔力（可理解为队伍生命值）。
- 一般情况下，每只精灵死亡会使本方魔力减少；通常魔力归零即失败。
- 某些精灵特性可以使死亡不扣魔力，或使死亡额外扣除魔力。
- 魔力扣除规则应由精灵特性和技能效果共同决定，不能在模拟器中写死为“一次死亡固定 -1”。

### 2.2 可见信息

对手通常可见：

- 已带入场的精灵与队伍成员；
- 精灵特性；
- 对手已经使用过的技能。

对手通常不可见：

- 未使用过的技能；
- 性格；
- 三维培养；
- 具体属性面板。

可通过速度、实时伤害、技能效果等战斗事实反推对手养成，但推断结果只能作为后验，不应覆盖人工确认事实。

## 3. 行动与回合顺序

### 3.1 基础排序

- 行动主要由速度决定。
- 技能拥有额外的先手值、后手值，且可能拥有连续行动效果。
- 速度相同的双方理论上随机决定先后，随机规则与是否每次重新随机 `【待校准】`。
- “应对”成功后，触发方必定先手。
- 先手、后手、连续行动、应对成功之间的组合优先级必须以具体技能实测补齐。

建议抽象为：

```text
行动排序键 = 应对成功 / 强制先手
           → 技能先手值 / 后手值
           → 速度
           → 同速随机
           → 连续行动队列
```

这只是当前建模顺序，不代表最终官方结算顺序，具体优先级标记为 `【待校准】`。

### 3.2 技能命中与伤害类型

- 所有技能必中。
- 不存在普通命中率、Miss、闪避和暴击判定。
- 伤害至少分为：物理伤害、魔法伤害、被动伤害。
- 存在反伤，但反伤目前主要由精灵特性提供。
- 属性相克存在，属性倍率应以现有属性数据 JSON 为基础；具体技能与特殊效果可能覆盖默认属性倍率。

### 3.3 应对机制

部分技能可以分别应对：

- 攻击；
- 防御；
- 效果。

应对条件满足后：

- 应对成功的技能必定先手；
- 如果被应对的精灵在应对结算前已经死亡，则该精灵原本要释放的技能无效；
- 应对成功、原技能失效、伤害/效果触发的先后顺序需要按技能逐条补录 `【待校准】`。

模拟器不能只把应对当作普通反击动作，必须保留“对方已宣告的动作”和“对方是否仍存活”两个判断条件。

## 4. 技能、冷却与精灵被动

### 4.1 精灵特性与技能特性

- 每只精灵都有自己的特性。
- 精灵特性可能改变对战机制，例如反伤、冷却、魔力扣除、入场触发或印记槽位。
- 特性可能影响结算，但不应默认改变基础行动排序；大体出手顺序仍由速度、先手值、后手值和其他行动机制决定。
- 技能自身也有特性。当前已知技能特性包括“应对效果”和“选择效果”，后续还需要按技能补充先手、后手、迅捷、连续行动、冷却修正等标签。
- 精灵特性和技能特性要分开存储、分开触发，避免把精灵被动错误地当成技能效果。

推荐的数据关系：

```text
sprite.trait      精灵固有特性，可能跨多个技能或多个回合生效
skill.traits      技能自身标签，随技能使用或应对条件触发
skill.effects     技能实际产生的伤害、状态、印记、天气等效果
```

特性具体是在宣告、排序、技能命中、技能结算、回合结束还是入场时触发，由各特性定义声明 `【待校准】`。

### 4.2 技能资源

- 普通技能没有 PP。
- 普通技能一般有 1 回合冷却。
- 防御技能通常有 1 回合冷却，但存在特殊防御技能，其被动可以减少一回合冷却。
- 存在精灵被动：使上一回合敌方使用的技能冷却一回合。
- 冷却减少、冷却刷新、冷却跳过和技能复制都可能受技能或精灵被动影响。

因此技能状态至少需要记录：

```text
skillCooldown
lastUsedTurn
cooldownReduction
cooldownSource
```

具体是“本回合结束减少”还是“使用后立即减少”暂为 `【待校准】`。

### 4.3 技能来源与技能池

每只精灵的可用技能由多个来源组成：

- **60 级自动技能**：精灵达到 60 级后自动学会自己的技能。
- **血脉技能**：与愿力冲击相关的技能或技能来源，具体释放条件、次数和冷却需要结合愿力机制补齐。
- **技能书技能**：通过技能书学习特定技能，属于可配置的技能池。
- **随机技能**：每回合替换为自己、己方队伍或对方的技能。

因此，精灵的技能配置需要区分“默认拥有”“血脉解锁”“技能书学习”和“临时随机替换”，不能只使用一个静态技能数组。

### 4.4 特殊技能形态

存在以下特殊技能形态：

- 随机变成自己、自己队伍或对手的技能；
- 使用后固定切换成某一类技能；
- 一个技能携带多个可选效果，由玩家在使用时选择释放；
- 具有迅捷、应对、连续行动等行动时序属性。

技能数据不能只保存一个固定 `actionClass`，还需要表达随机技能池、转换后的技能类型、可选效果和触发条件。

随机技能至少需要在状态中记录：

```text
randomSkillSource   self | allyTeam | enemyTeam
randomSkillId       本回合实际替换得到的技能
randomSkillTurn     生成该技能的回合
```

目前确认的是“每回合替换”。替换发生在回合开始、行动宣告前还是技能使用时，以及候选技能是否包含已知技能、默认技能、血脉技能和技能书技能，均为 `【待校准】`。

## 5. 属性与养成

### 5.1 属性来源

每只精灵的战斗属性由至少以下部分组成：

- 精灵天生的个体值 / 种族属性；
- 性格；
- 三维培养；
- 等级；
- 强化、弱化、技能效果、特性和天气。

### 5.2 性格

- 普通属性性格通常是一个属性 `+10%`、另一个属性 `-10%`。
- 生命相关性格目前口述为 `+20%`，对应的负向倍率与适用范围需要查站点资料并真机确认 `【待校准】`。
- 性格不可从对手面板直接看到，需要从速度和伤害等观测进行后验判断。
- 性格种类较多，当前 `data/stats.json` 的性格表不应视为完整最终表，需要从 `roco.world` 资料补齐并逐项核对。

### 5.3 三维培养

> ⚠️ 已按官方口径重整：所谓「三维」即**个体值（天分）**，可分配到任意 3 项，每项 0~60（5★×6）。权威定义见《数值与伤害模型-设计-v0.1》。

- 三维是加点机制，可分配到体力、攻击、防御等属性。
- 每个培养等级对应 `+10`，5 星、60 级的常见 PVP 配置对应最高 `+60`。
- 三维最多可以加到三个属性上。
- 当前口述规则是“体力 / 攻击 / 防御三面板”，是否能将三维分配到魔攻、魔抗、速度需要进一步确认；现阶段按三面板建模。
- PVP 常见基准为 60 级、5 星资质。

三维加点应作为结构化事实存储，而不是直接改写精灵基础数据：

```text
profile = {
  nature,
  training: {
    hp,
    atk,
    defense
  }
}
```

### 5.4 本系威力加成

- 当前记为：本系技能威力可能有 `+25%` 加成。
- 该加成的适用条件、是否只针对攻击技能、是否与属性克制独立相乘尚未确认。
- 在真机验证前，数据中保留为 `【待校准】`，不得固化为最终公式。

## 6. 强化、弱化与状态

### 6.1 强化与弱化

强化类型至少包括：

- 百分比属性变化；
- 固定数值属性变化；
- 技能威力变化。

Buff / debuff 层数上限通常为 99。不同效果的叠加、覆盖、刷新和清除规则可能不同，应由具体效果声明。

### 6.2 已知状态

| 状态 | 当前规则 | 换人 | 备注 |
| --- | --- | --- | --- |
| 中毒 | 持续存在，造成持续伤害 | 消失 | 伤害结算时机与数值 `【待校准】` |
| 烧伤 | 每回合掉当前生命的一半 | `【待校准】` | 需确认是当前生命、最大生命，还是固定比例 |
| 睡眠 | 当前规则中暂不存在 | - | 不加入默认状态池 |
| 冰冻 | 一层冻结 5% 生命 | 随精灵保留 | 先手冰冻可能直接触发死亡 |
| 麻痹 | 暂未使用 | - | 暂不加入默认状态池 |
| 恐惧 | 暂未使用 | - | 暂不加入默认状态池 |
| 限制离场 | 默认 3 回合不能换人 | 随限制来源处理 | 具体解除条件 `【待校准】` |

一般伤害性状态在回合结束结算，但先手冰冻等效果可以在技能结算阶段直接造成死亡。状态可以叠加、被免疫、被覆盖，状态伤害也可能被抵抗。

## 7. 印记、天气与场地效果

### 7.1 印记

- 印记是持久性、全队通用的状态，不等同于单只精灵身上的普通状态。
- 每个队伍通常支持一个正面印记和一个负面印记。
- 部分精灵特性可以突破这个数量限制，同时存在多个印记。
- 印记如果没有被清理，通常会永久存在。
- 印记可以覆盖，覆盖规则取决于具体印记。
- 对手主动入场时，可能触发对方印记造成伤害或其他限制。

引擎需要区分：

```text
spriteStatus  精灵个体状态，可能随换人清除或随精灵保留
teamMark      队伍通用印记，默认持久存在
weather       当前天气，可能被新天气顶掉
```

### 7.2 天气

已知天气：

- 雨天；
- 暴风雪；
- 沙尘暴；
- 雷暴天。

不同天气提供不同加成或效果。天气通常会被其他天气顶掉；雨天目前存在延迟相关机制。每种天气的持续时间、覆盖优先级、延迟含义和具体倍率均需从站点资料及实战补齐 `【待校准】`。

## 8. 换人与入场

- 普通手动换人占用本回合。
- 换人优先级高于普通攻击。
- 存在带“迅捷”特性的技能：手动换人入场时可以释放，相当于不额外消耗回合。
- 死亡后的强制换人不占回合。
- 入场会触发限制入场的印记或特性，例如对方主动入场造成伤害。
- 换人时哪些状态消失、哪些状态随精灵保留，必须按状态定义区分。

## 9. 对手推断模型

对手模型需要同时维护“行为”和“养成”两类后验，不能混成一个计数器：

### 9.1 行为后验

根据对手已使用动作更新攻击 / 防御 / 状态等动作分布。应保留精灵维度，因为同一个对手玩家使用不同精灵时行为可能不同。

### 9.2 养成后验

根据以下事实估计对手性格和三维：

- 速度排序与先手结果；
- 已知技能造成的实时伤害；
- 对手受到的伤害；
- 生命上限或当前生命变化；
- 已知天气、强化、属性克制和特性。

观测到的事实应分为两类：

- 对手做了什么：更新对手行为模型；
- 对手实际表现出什么数值：校准精灵 / 技能 JSON，或更新养成后验。

## 10. 当前模拟器需要调整的方向

1. 把技能冷却、后手值、连续行动、应对成功和被应对者死亡纳入行动队列。
2. 移除所有普通命中、Miss、暴击、闪避分支；保留属性抵抗、特性反伤和状态伤害抵抗。
3. 将普通状态、精灵个体状态、队伍印记、天气分成独立状态域。
4. 将换人分为普通手动换人、迅捷换人、死亡强制换人三种动作。
5. 把魔力扣除抽象成可由特性 / 技能覆盖的规则。
6. 完善 `stats.json` 的性格与三维定义；当前占位系数必须经过实测。
7. 为技能数据增加“随机技能、转换技能、多选一效果、应对目标、冷却修正”等字段。
8. 在每回合事件日志中记录：行动排序依据、技能冷却变化、应对结果、状态伤害、印记覆盖、天气覆盖、魔力变化和入场触发。

## 11. 待补问题清单

### 优先级 A：影响核心模拟

- 物理 / 魔法 / 被动伤害的具体公式。
- 先手值、后手值、速度、连续行动、应对成功之间的完整排序。
- 技能冷却的减少时机和最低值。
- 冰冻层数的叠加规则、5%生命的计算基准、死亡时机。
- 烧伤“每回合掉一半”的生命计算基准。
- 魔力扣除与特性覆盖规则。
- 四种天气的具体效果、持续时间、延迟和覆盖规则。

### 优先级 B：影响状态与队伍

- 中毒、限制离场的持续时间与清除条件。
- 普通状态换人后的清除 / 保留完整表。
- 印记槽位被特性突破时的上限和覆盖顺序。
- 迅捷技能在入场触发时与入场印记、速度排序的先后。
- 死亡换人与入场触发的完整顺序。

### 优先级 C：资料补齐

- 从 `roco.world` 补全性格名称、正负向属性和生命倍率。
- 校验 60 级 5 星、三维每级 `+10` 与最高 `+60` 的面板换算。
- 核实本系技能威力 `+25%` 是否存在及其作用范围。
- 按技能逐条补充动作类型、冷却、应对关系、随机 / 转换技能和多效果选择。

## 12. 推荐的后续录入顺序

1. 先补一套最小可验证技能：普通物理、普通魔法、防御、应对攻击、应对防御、状态、迅捷换人。
2. 用固定双方精灵和固定养成录入完整一回合，确认行动排序与冷却变化。
3. 再补四种天气、印记和入场触发。
4. 最后补随机技能、多效果选择、复杂被动和养成后验。
