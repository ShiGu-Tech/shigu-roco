# 战斗机制扩展层 · 设计 v0.1

> 文档状态：设计 ✅ v0.1 · 代码 🟡 第一阶段 · 验证 ✅ 自动化基础验证 · 生产 🟡 本机可用

## 1. 定位与目标

战斗机制扩展层用于描述和执行“技能、精灵特性、血脉技能、印记、天气”等对基础战斗机制的改变。

它解决的问题不是保存某个技能的文本描述，而是把以下变化变成可组合、可追踪、可回放的机制：

- 修改伤害、属性、冷却、状态和印记；
- 改变行动先后、插入额外行动、取消已宣告动作；
- 在攻击、防御、效果、入场、死亡等事件上进行应对；
- 生成、替换、交换和复制技能；
- 修改天气、魔力、换人限制和队伍规则；
- 在不重写回合引擎的情况下接入新技能与新特性。

本文是扩展层设计稿。具体技能和特性逐个确认后，落到 `data/*.json`，复杂机制通过受控的专用处理器实现。

## 2. 设计原则

1. **基础内核稳定**：回合阶段、状态快照、行动队列、随机源、事件日志和终局判定由核心固化。
2. **效果数据化**：常见机制使用结构化 `trigger + when + effects` 描述，不为每个技能写独立分支。
3. **机制可变**：扩展可以修改状态和行动流程，但只能通过受控命令提交，不能直接任意修改对象。
4. **效果可组合**：一个技能或特性可以产生多个效果；一个效果可以继续触发其他效果。
5. **顺序显式化**：每个触发点、行动插入、动作取消和状态变更都有确定优先级与来源。
6. **失败可见**：暂不支持的效果必须产生 `unsupported-effect` 事件，不能静默忽略。
7. **回放优先**：每个扩展命令记录来源、触发事件、目标、旧值、新值和随机结果。
8. **数据与代码解耦**：游戏数值和普通机制进入 JSON；只有无法稳定表达的复杂算法才进入 TypeScript 处理器。

## 3. 分层架构

```text
BattleState
    │
    ├─ BattleKernel       固化回合阶段、终局、快照、基础伤害入口
    ├─ ActionQueue        管理排序、插入、取消、连续行动和应对先手
    ├─ TriggerBus         发布回合/动作/伤害/状态/入场/死亡事件
    ├─ MechanismRegistry  注册技能、精灵特性、印记、天气扩展
    ├─ EffectInterpreter   执行通用条件和效果命令
    ├─ RuleModifier        管理临时机制修正和优先级
    └─ EventLog            记录每个触发、命令、状态变更和未支持效果
```

### 3.1 固化在核心的内容

- 战斗状态不可变快照与 copy-on-write；
- 回合阶段和阶段转换；
- 行动宣告、行动排序、行动执行、动作取消；
- 速度、先手值、后手值、同速随机和连续行动的基础排序入口；
- 技能冷却、状态、印记、天气、技能池、魔力和队伍的状态容器；
- 伤害计算入口与属性克制入口；
- 触发器分发、效果命令提交和事件日志；
- 随机源、终局判定、死亡和基础换人流程。

### 3.2 由扩展提供的内容

- 触发条件；
- 目标选择；
- 伤害或治疗修正；
- 状态、印记、天气和冷却修改；
- 行动优先级、额外行动、动作取消；
- 技能池生成、复制、转换、交换；
- 入场、死亡、应对和特殊魔力规则；
- 具体数值与具体技能语义。

## 4. 统一机制描述

### 4.1 扩展定义

每个技能、特性或印记可以拥有一个或多个机制扩展：

```ts
type MechanismDefinition = {
  id: string;
  ownerType: "skill" | "trait" | "mark" | "weather" | "system";
  ownerId: string;
  trigger: TriggerDefinition;
  when?: Condition[];
  effects: EffectDefinition[];
  priority?: number;
  oncePerTurn?: boolean;
  sourceVisibility?: "public" | "private";
};
```

实际 JSON 使用 camelCase；上面的 TypeScript 仅表达契约，不要求每个字段都对所有机制开放。

### 4.2 触发器

初始触发器按战斗生命周期划分：

```text
battleStart
turnStart
actionDeclared
beforeActionOrder
actionOrderResolved
beforeAction
actionResolved
beforeDamage
afterDamage
beforeEffect
afterEffect
beforeSwitch
afterSwitch
beforeDeath
afterDeath
turnEnd
battleEnd
```

还需要支持带对象的细分事件，例如 `skillUsed`、`statusApplied`、`markApplied`、`weatherChanged` 和 `skillCooldownReduced`。触发器只描述“什么时候通知扩展”，不直接决定效果。

### 4.3 条件

条件用于限制扩展是否生效，初始支持对象、事件、数值、状态、关系和逻辑条件：

```text
对象：self / target / ally / enemy / active / team / field
事件：actionType / skillId / element / damageType / status / mark / weather
数值：hpRatio / maxHp / speed / stat / stage / cooldown / turn
状态：alive / hasStatus / hasMark / canSwitch / skillReady
关系：isWeakTo / isResistedBy / sameElement / sameTeam
逻辑：all / any / not
```

条件只读状态，不能产生副作用。

## 5. 效果命令模型

扩展不直接操作 `BattleState`，而是生成效果命令。核心验证命令合法后，再以事务方式应用。

### 5.1 基础效果

```text
dealDamage             造成物理 / 魔法 / 被动 / 固定 / 百分比伤害
heal                   治疗
modifyStat             修改基础属性、战斗属性或强化等级
modifyPower            修改技能威力
applyStatus            施加状态
removeStatus           移除状态
applyMark              添加或覆盖印记
removeMark             移除印记
changeWeather          设置、延迟或覆盖天气
modifyCooldown         增加、减少、刷新或跳过冷却
modifyMagic            修改队伍魔力
modifySwitchLock       增加、减少或解除限制离场
```

### 5.2 行动效果

```text
setPriority            修改本次动作的先手 / 后手值
forceFirst             强制当前动作先手
insertAction           在行动队列插入额外动作
grantExtraAction       允许当前单位连续行动
cancelAction           取消已宣告但尚未执行的动作
replaceAction          替换本回合动作
forceSwitch            触发强制换人
allowSwitch            允许被限制的换人
```

### 5.3 技能池效果

```text
learnSkill             加入永久或临时技能
forgetSkill            移除技能
replaceSkill           将技能替换为另一个技能
copySkill              复制来源单位的技能
randomizeSkill         从技能池随机生成临时技能
swapSkillSet           交换双方或指定单位的全部技能
```

技能池效果需要声明作用范围、持续时间、是否公开以及换人后是否保留。

## 6. 事务与结算

一次技能或特性触发经历以下过程：

```text
1. 发布事件
2. 收集符合条件的机制扩展
3. 按优先级和来源顺序排列扩展
4. 执行条件求值
5. 生成 EffectCommand 列表
6. 核验目标、权限、状态和互斥关系
7. 按结算顺序应用命令
8. 触发后续事件
9. 写入事件日志
10. 必要时重新计算行动队列
```

### 6.1 原子性与死亡检查

- 每个效果命令是一个可记录的最小变更。
- 一个技能的效果列表默认按声明顺序执行。
- 伤害结算后立即检查死亡；后续效果是否继续由技能或机制定义。
- 目标死亡后，面向该目标的后续效果默认取消，并记录取消原因。
- 被应对动作命中的原动作，在执行前重新检查施法者存活、动作有效性和技能冷却。

事务是处理“应对抢先手”“被应对者死亡导致原技能无效”“一个技能同时改伤害、技能池和冷却”等场景的必要边界。

## 7. 行动队列设计

行动队列是扩展层可以影响流程、但不能直接破坏核心的边界。

```ts
type QueuedAction = {
  id: string;
  actorId: string;
  action: BattleAction;
  declaredAt: number;
  priority: number;
  speedSnapshot: number;
  source?: string;
  status: "queued" | "cancelled" | "executing" | "resolved";
};
```

扩展只能通过 `enqueueAction`、`cancelAction`、`setActionPriority`、`forceActionFirst` 和 `replaceAction` 修改队列。

重新排序时保留原始宣告顺序、当前优先级、速度快照、强制先手来源、同速随机数和是否为额外行动，从而能解释“为什么这个技能先手”，并让 MCTS 复现同一行为。

## 8. 技能池与可见性

### 8.1 技能池结构

```ts
type SkillSlot = {
  skillId: string;
  source: "autoLevel" | "bloodline" | "skillBook" | "random" | "copied" | "swapped";
  learnedAt?: number;
  expiresAt?: number;
  revealed: boolean;
};
```

技能池需要区分 60 级自动技能、血脉技能、技能书技能、随机生成的临时技能以及复制或交换得到的技能。

### 8.2 信息不完全

引擎维护两套视图：

- `trueState`：模拟器内部完整状态；
- `beliefState`：某一方当前可见的信息与对隐藏信息的后验。

技能池交换、随机技能和对手隐藏技能必须同时更新实际技能池、对手已知技能集合、事件可见字段和 MCTS 隐藏状态采样分布。

## 9. 示例

### 9.1 应对防御

```json
{
  "id": "skill-counter-defense",
  "ownerType": "skill",
  "ownerId": "example-counter",
  "trigger": "actionDeclared",
  "when": [{ "path": "event.action.type", "op": "eq", "value": "defense" }],
  "effects": [
    { "type": "forceFirst" },
    { "type": "cancelAction", "target": "event.actor" },
    { "type": "dealDamage", "damageType": "physical", "power": 100 }
  ]
}
```

实际是否在宣告时锁定、被应对者死亡后原技能如何处理，由核心的动作有效性检查负责。

### 9.2 每回合随机生成技能

```json
{
  "id": "random-skill-every-turn",
  "ownerType": "skill",
  "ownerId": "example-random",
  "trigger": "turnStart",
  "effects": [{
    "type": "randomizeSkill",
    "source": ["self", "allyTeam", "enemyTeam"],
    "duration": "thisTurn",
    "visibility": "revealedOnUse"
  }]
}
```

候选技能是否包含未展示技能、血脉技能和技能书技能，需要在具体技能定义中声明 `【待校准】`。

### 9.3 交换全部技能

```json
{
  "id": "swap-all-skills",
  "ownerType": "skill",
  "ownerId": "example-swap",
  "trigger": "beforeAction",
  "effects": [{
    "type": "swapSkillSet",
    "from": "self",
    "to": "enemy",
    "duration": "battle"
  }]
}
```

交换类效果必须记录交换前后技能池，并明确是否交换临时技能、是否保留技能来源、是否换人后恢复，以及对手何时获得可见信息。

## 10. 专用处理器边界

通用效果无法表达的机制允许使用专用处理器，但必须实现统一接口：

```ts
type MechanismHandler = {
  id: string;
  canHandle(definition: MechanismDefinition): boolean;
  evaluate(context: MechanismContext): EffectCommand[];
};
```

专用处理器不能直接写入 `BattleState`，必须使用注入的随机源，写明输入、输出和来源，并在处理不了时返回明确的 unsupported 结果。适合专用处理器的场景包括复杂技能转换、全技能交换、跨多个事件的特殊特性和需要搜索候选状态的效果。

## 11. 错误、未知和未支持机制

未知机制不能当作无效果处理。事件日志至少记录：

```json
{
  "type": "unsupported-effect",
  "sourceId": "skill-or-trait-id",
  "effectType": "unknown-effect",
  "phase": "beforeAction",
  "impact": "simulation-incomplete"
}
```

推荐结果需要带出是否存在未支持效果、受影响的动作或状态，以及模拟结果是否只能作为低置信度参考。

## 12. 版本化与校准

- 机制定义带 `mechanismVersion`；
- 数据 JSON 带 `dataVersion`；
- 事件日志记录规则版本、数据版本和随机种子；
- 真机对拍发现规则变化时，只新增版本或新增字段，不修改历史回放的语义；
- 尚未确认的倍率、触发时机和候选池用 `【待校准】` 或 `confidence` 标识。

## 13. 非目标

- v0.1 不尝试一次性覆盖所有技能和特性；
- 不把每个自然语言技能描述自动转换为完整正确的效果；
- 不允许任意脚本直接执行文件、网络或 DOM 操作；
- 不把复杂机制偷偷降级为“忽略效果”；
- 不在本设计稿中确定具体技能的最终数值。

## 14. 实施顺序

1. 把现有 `BattleState` 拆出技能池、行动队列、事件日志和状态域。
2. 建立 `TriggerBus`、`EffectCommand` 和事务应用器。
3. 迁移普通伤害、属性、状态、印记、天气、冷却到通用效果。
4. 接入行动队列修改：先手、取消、连续行动、强制换人。
5. 接入技能池修改：随机技能、复制技能、交换全部技能。
6. 接入专用处理器注册表和 unsupported 事件。
7. 用逐回合回放测试替换只看最终胜负的测试。
8. 再按精灵和技能逐个补充具体机制。
