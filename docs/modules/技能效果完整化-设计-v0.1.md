>
> 上游：《战斗机制扩展层-设计-v0.1》（触发器 / 条件 / 效果命令 DSL）、《伤害模型补齐-设计-v0.1》（伤害修饰通道）、《数值与伤害模型-设计-v0.1》（主公式，已封版）。本稿只补「技能 / 特性 / 印记 / 天气的效果可执行性」，不改主公式与面板。

## 1. 定位与边界

**现状**：注册图鉴共 **579** 技能，只有「类别为物理 / 魔法且威力 > 0」的 **358** 条由 `engine/server.ts:22-31` 自动生成 `dealDamage` 机制；其余 **221** 条（状态 167 + 防御 54）**没有任何机制、在对局中完全不生效**。另有 **40** 条特性为 `effects: []` 空占位、印记 4 / 天气 2 的细节结算未齐。

**目标**：把图鉴中全部技能、特性、印记、天气的「中文说明」补齐为**可执行机制**，使模拟器对任意动作都能给出真实结算（能算准的算准，算不了的显式 `unsupported` + `【待校准】`）。

**不在本稿**：
- 伤害主公式与各项倍率口径（见《数值与伤害模型》《伤害模型补齐》）。
- 面板换算、养成、MCTS 搜索、前端展示。
- 外部图鉴本身的数据采集（见《图鉴数据同步》）。

**与注册机制的关系**：技能**基础数据**（名称 / 属性 / 类别 / 威力 / 能耗 / 冷却 / 说明 / 图标）来自 `data/registry/catalogs/`；技能**效果**目前只能靠 `data/mechanisms.json` 手工登记。本稿既要补效果本身，也要为「效果可随图鉴注册」铺路（§4.5）。

## 2. 设计原则

1. **数据驱动，代码只做解释器**：效果一律写进 `data/mechanisms.json`（长期可扩到注册快照），引擎不出现任何具体技能 / 特性 / 倍率魔法数字。
2. **通用底座优先**：先做「状态按侧 turnEnd 结算、层数上限与衰减、条件逻辑 / 免疫 / 概率」等可复用能力，再逐条转写具体技能，避免为单个技能打补丁。
3. **算不准不猜**：无实测口径的效果登记 `unsupported` 并保留原文，在 `params.note` 标 `【待校准】`。
4. **术语即字典**：图鉴说明里的 `<desc_id=N>词条</>` 是官方术语（`glossary`，共 53 条），优先解析为机制引用，减少对自由文本的猜测。
5. **可回归**：每个新 effect / 触发器走独立单测，行为同输入可复现。
6. **无兼容包袱**：本项目单人离线、无历史存档约束，直接按最终模型重构——`statuses` 只存**层数**、废弃「duration 混存」与回合末无脑 `-1` 衰减、废弃全局单次 turnEnd，**不写兼容分支**。

- **效果未结构化**：外部图鉴只给中文 `description`，无结构化效果字段；221 技能 + 40 特性需转写。

## 4. 领域模型 / 契约

### 4.1 效果的两层来源

```text
注册图鉴（data/registry/catalogs/）
  ├─ 技能基础数据 ──────────────→ 自动生成「攻击技能 dealDamage」（现有）
  └─ glossary 术语 + 说明 ──────┐
                                ├─→ 机制扩展层 effects（data/mechanisms.json → 长期可入快照）
机制扩展层（data/mechanisms.json）┘
  ├─ ownerType: trait / mark / weather（人工登记）
  └─ ownerType: skill（目前装配时被过滤，技能以图鉴现算）
```

目标：技能效果与图鉴同源、可注册；短期先落 `data/mechanisms.json` + 术语解析，长期见 §4.5。

### 4.2 DSL 扩展（新增 / 补齐）

在 `mechanisms/types.ts` 上**直接重构**（不留兼容分支）：

```ts
// 0) 概率：所有 effect 可带 chance（0~1），runtime 用「种子 + 机制 id + 回合」确定性掷点
export type EffectDefinition = EffectSpec & { chance?: number };

// 1) 状态 = 层数；结算 / 衰减由机制声明，不再混存 duration
| { type: "applyStatus"; statusId: string; layers?: number; immuneElements?: string[] }
| { type: "settleStatus"; statusId: string; decayLayers?: "half" | "clear"; delta?: number }
| { type: "settleMark"; markId: string; decayLayers?: "half" | "clear"; delta?: number }
| { type: "removeStatus"; statusId: string }

// 2) 伤害带元素（DoT 用 percentMaxHp + element 做免疫）
| { type: "dealDamage"; target?: string; category: ...; power: number; element?: string; ... }

// 3) 冷却作用域：scope=defense 时作用于该精灵所有防御技能
| { type: "modifyCooldown"; skillId?: string; scope?: "skill" | "defense"; delta: number; minimum?: number }

// 4) 增益层数上限（上限值来自 rules.stage.cap）
| { type: "modifyStat"; stat: string; mode: "flat" | "percent"; value: number; maxStages?: number }

// 5) 动态威力 / 星陨（后续批次）
| { type: "setPowerTier"; tiers: number[]; source: "layers" | "uses" | "turn" }
| { type: "starfall"; basis: "stack"; element: string }
```

**应对不引入新命令**：应对 = `actionDeclared` 上的**条件 + `forceFirst`**，对手动作经 `event.opponentAction` 暴露。

条件扩展（`Condition`）：

```ts
type Condition =
  | { allOf: Condition[] } | { anyOf: Condition[] } | { not: Condition }
  | { path: string; op: "eq" | ... | "has"; value?: unknown; valueFrom?: string /* 比较值取自上下文路径，如 state.turn */ };
```

### 4.3 结算阶段（最终设计）

回合顺序：

```text
① battleStart
② turnStart（全局）
③ wish
④ switch
⑤ 宣告：enqueue → actionDeclared（event 带 opponentAction）→ ordered   ← 应对在此改队列
⑥ 每行动：beforeAction → executeSkill
     伤害：beforeDamage → dealDamage → onHit(通用) → 印记 → afterDamage
     → skillUsed → actionResolved
⑦ 回合末：for side in [player, enemy]: turnEnd(actorSide=side) → turnEnd 全局
     → settleMarks → 环境衰减（天气 / 冷却 / switchLock / wish / skillOverrides）→ faint
⑧ turn++
```

- **状态按侧结算**：turnEnd 按侧派发；状态 DoT / 衰减写在 `ownerType:"system"` 机制里（`settleStatus` + `dealDamage percentMaxHp`）。**不再无脑 `statuses-1`**；未声明机制的状态不衰减。
- **免疫**：effect 的 `immuneElements` 与目标精灵系别比对，命中即免疫（站点 `statusImmunities` 为空，故由机制数据声明，如灼烧 `["Fire"]`）。
- **应对 / 先手**：`actionDeclared` 条件命中 → `forceFirst` + 应对效果（火焰护盾即一组数据条目）。
- **命中链**：`onHit` 通用派发（技能级）；印记遍历保留。
- **触发器补派发**：`beforeActionOrder` / `actionOrderResolved` / `beforeEffect` / `afterEffect` / `weatherChanged` / `skillCooldownReduced` / `battleEnd`。

### 4.4 术语解析（`desc_id` → 机制引用）

- 同步 / 注册时保留技能 `description` 的 `<desc_id=N>` 标记；引擎提供 `resolveDescription(skill, glossary)` 输出「术语 token + 自由文本」序列。
- 建立术语 → 机制的映射表（如 `1016 应对攻击 → setCounter(kind:"attack")`、`1002 灼烧 → applyStatus("burn")` + `settleStatus`、`1015/1017 应对状态/防御`、`3007 暴风雪 → 天气回合结算`）。
- 纯文字技能（52 条）保留 `unsupported` + 原文，供人工/AI 逐步转写。

### 4.5 结构化注册（长期）

在 `ExternalSnapshot` / `RegisteredCatalog` 增加可选 `effects` / `mechanisms` 字段：由上游或「阶段 5 自动解析」产出，注册时随图鉴入库，`server.ts` 直接采用（替代当前的手工 `mechanisms.json` 技能段）。这是「技能说明自动转效果」的最终形态。

### 4.6 冷却子系统

同一套「冷却计数器」要覆盖 5 个来源：

| 来源 | 类型 | 效果 | 目标 | 方向 |
| --- | --- | --- | --- | --- |
| 火焰护盾 `sk-7040300` | 火·防御 | 应对攻击 → 防御技能冷却 | 自身全部防御技能 | **+1** |
| 壁垒 `sk-7080240` | 地·防御 | 减伤 90%，应对攻击 → 防御技能冷却 | 自身全部防御技能 | **−1** |
| 破防 `sk-7140160` | 武·状态 | 双防 −70%，应对防御 → 被应对技能冷却 | **对手被应对的技能** | **+2** |
| 上锁 `sp-380-1` | 特性 | 敌方本回合使用的技能，冷却 | **对手本回合使用的技能** | **+1** |
| 入梦 `sk-7170300` | 幽·状态 | 敌方下回合回能 −5，自身 | 自身该技能 | **+2** |

**规则**（含「占场消耗」）：

1. 冷却记在**精灵**上（`ActiveSprite.cooldowns`），跟随上下场；**换人不重置、不冻结归零**。
2. **占场消耗**：冷却只在精灵**在场（active）**时按回合递减；下场（bench）**冻结**，重新上场后从剩余值继续。
   - 例：T1 用防御（置 +1）→ T2 换下 → T3 换上仍剩余 1，仍不能用；T3 在场结算后才归 0。
3. 回合末 tick：只对**当前 active** 且**本回合未被置/改**的技能递减（per-side `cooldownTouched` 集合，回合末清空），修「刚置就被同回合 tick 吃掉」的 off-by-one。
4. ±N 立即生效并 clamp `[0, ∞)`；`−1` 对已 0 的技能无效果。

**DSL**：`modifyCooldown` 增加 `skillIdFrom?: string`（动态取目标技能，如 `event.opponentAction.skillId`），支撑破防 / 上锁；`scope:"defense"` 支撑火焰护盾 / 壁垒。

### 4.7 状态 / 印记 / 天气三分类

图鉴 glossary 的 54 个术语混在同一命名空间，引擎按**语义**拆为三类互斥项（`catalog/normalize.ts`）：

| 类型 | 判定 | 例子 | 引擎字段 | 换人 |
| --- | --- | --- | --- | --- |
| **状态 / buff** | `STATUS_KEYS`（回合结算的增益 / 减益 / DoT） | 中毒 1001、灼烧 1002、冻结 1004、萌化 1006、寄生 1008、引电 3022、禁足 3023、木桶 3024、月陨星 3025 | `ActiveSprite.statuses`（只存层数） | 默认清除；`rules.status.persistOnSwitch = ["freeze","moe"]` 保留 |
| **印记** | `MARK_KEYS` | 1014 / 1018 / 1019 / 1021 / 1022 / 1023 / 1027 / 1028 / 1030 / 1031 / 1032 / 1035 / 3012 / 3020 | `marks` / `teamMarks` | 「正负各 1 / 继承」待核 |
| **天气** | `WEATHER_KEYS` | 沙暴 3006、暴风雪 3007、雨天 3008、雷鸣 3021 | `weather` | 回合衰减 |

- **key 取站点 `icon_key`**（如 `burn` / `poison` / `starfall-mark`），归一化后作为机制 `ownerId` 与对局字段键。
- **注册表按 `registrationId`（含 `NORMALIZER_VERSION`）缓存** `catalog.json`；normalizer 语义变更必须 bump 版本号才会重跑（本次 n5 → n6）。
- 三类在注册表 `catalog.json` 与静态 `bundle.json` 中各有独立 `statuses` / `marks` / `weather` 字段；`bundle.json` 只含**被机制引用**的条目，全量清单在注册表里供 `/data` 展示。
- 换人清理在 `battle.doSwitch` 调 `clearStatusesOnSwitch`；`rules.status = { clearOnSwitch: true, persistOnSwitch: ["freeze","moe"] }`。永久增减益的换人模型仍 `【待校准】`。

## 5. 关键决策

1. **先用 `data/mechanisms.json` 落地，再扩注册协议**：不阻塞开发，同时保留升级路径（§4.5）。
2. **通用结算底座先行**：把「按侧 turnEnd + 状态 DoT + 层数 + 条件逻辑 / 免疫 / 概率」做成通用能力，之后每个技能只是数据条目。
3. **应对 / 先手单独一批**：84 条占比最高、且牵动行动队列，独立设计实现。
4. **术语字典优先于文本猜测**：169 条带术语引用的技能走映射表；52 条纯文字延后人工。
5. **算不准不猜**：一切未实测口径 `unsupported` + `【待校准】`。
6. **无兼容包袱**：直接改 `statuses` 语义、拆 `decay`、改 turnEnd 为按侧；不保留旧字段与旧分支。
7. **应对不新增命令**：用「`actionDeclared` 条件 + `forceFirst`」表达应对与必定先手，避免为单一术语造新命令。

## 6. 非目标

- 不改伤害主公式与面板换算。
- 不做暴击 / 命中随机（本项目口径：必中、无暴击）。
- 不在本稿做 MCTS 策略或落子启发。
- 不追求一次性补全 221 技能 + 40 特性：按批次推进，未定项占位。
