# 引擎可改性 · 设计 v0.1

## 1. 定位与边界

- **定位**：把引擎改造为**「极简解释器 + 可替换定义」**，使引擎**自身行为**（回合流程、伤害公式、触发/条件/效果）可在**不改 `engine/**` 源码**的前提下定义、替换、版本化、试跑。
- **一句话判据**：能用「解释器已支持的词汇 + 数据」表达的行为，一律进数据；只有**新语义/新算法**才写代码（并 bump `ENGINE_VERSION`）。
- **边界**：
  - 不改：外部图鉴同步、DSH / 站点数据、决策层（MCTS）搜索语义（可后续）。
  - 不提供：可在数据里写**任意代码/脚本**（安全红线，见 §7）。
- **与既有文档的关系**：本稿是**架构改造**（引擎本体）；《引擎工作台》是建立在其上的**可视化 + 版本管理 UI**。

## 2. 设计原则

1. **解释器极简且固定**：核心只剩四件事——驱动流程、求值条件、执行效果、读写状态。它不认识任何具体技能 / 精灵。
2. **策略进数据**：回合流程、伤害公式、系数/倍率表、机制注册 → §3 的各类 Spec。
3. **指令集可插拔**：`trigger` / 条件算子 / `effect` / 流程 op 都是**注册表**；内建与扩展走**同一** `EngineExtension` 接口。
4. **确定性可钉版本**：任何一局结果由 `{ engineVersion, specVersion, dataVersion, bundleHash }` 唯一决定。
5. **单一事实源**：迁移后删除旧硬编码，不留「代码 + 数据」两套并行逻辑。
6. **无 `eval`**：表达式是**封闭算子、纯数值、无副作用**的 AST，不是脚本。

## 3. 目标架构分层

```text
┌─────────────────────────────────────────────────────────────┐
│  定义层（数据 / 可版本化 / 可编辑）                          │
│  · mechanisms.json  规则：谁在哪个 trigger + when + effects  │
│  · pipeline.json    回合流程：阶段顺序 + 触发时点             │
│  · formula.json     伤害公式：表达式 AST + 系数               │
│  · rules/stats/...  既有数据                                 │
├─────────────────────────────────────────────────────────────┤
│  指令集层（代码 / 可插拔注册表 EngineExtension）             │
│  · triggers   注册的触发点                                   │
│  · operators  条件算子                                       │
│  · effects    效果处理器（dealDamage / rotateLoadout / …）    │
│  · pipelineOps 流程算子（dispatchTrigger / resolveQueue / …） │
├─────────────────────────────────────────────────────────────┤
│  解释器层（代码 / 极简固定）                                 │
│  · Engine：按 pipeline 驱动 → dispatch → evaluate → execute   │
└─────────────────────────────────────────────────────────────┘
        ↑ 由 EngineBundle 实例化；可 reload / 隔离沙盒
```

## 4. 领域模型

### 4.1 `EngineBundle`（可实例化、可版本化的引擎定义）

```ts
interface EngineBundle {
  engineVersion: string;     // 解释器/指令集代码版本（ENGINE_VERSION）
  specVersion: string;       // 定义层整体版本（pipeline+formula+mechanisms+extensions manifest）
  bundleHash: string;        // 内容哈希，供回放/试跑精确比对
  pipeline: PipelineSpec;
  formula: FormulaSpec;
  mechanisms: MechanismDefinition[];
  extensions: string[];      // 启用的扩展 id（内建即扩展）
  // 既有数据：sprites / skills / statuses / marks / weather / elements / rules / stats / assets
}
```

### 4.2 `PipelineSpec`（回合流程 = 数据）

`step()` 现为命令式硬编码；改为**阶段表**，每阶段引用一个**流程算子**（固定词汇）：

```json
{
  "version": "1.0.0",
  "turn": [
    { "id": "start",   "op": "dispatchTrigger", "trigger": "turnStart", "sides": "both" },
    { "id": "pending", "op": "runPendingEffects", "timing": "turnStart" },
    { "id": "wish",    "op": "wishPhase" },
    { "id": "switch",  "op": "switchPhase" },
    { "id": "declare", "op": "declareActions" },
    { "id": "resolve", "op": "resolveQueue", "action": [
        { "id": "before", "op": "dispatchTrigger", "trigger": "beforeAction" },
        { "id": "run",    "op": "executeAction" },
        { "id": "after",  "op": "dispatchTrigger", "trigger": "actionResolved" }
    ] },
    { "id": "endTrig", "op": "dispatchTrigger", "trigger": "turnEnd", "sides": "both" },
    { "id": "pendingEnd", "op": "runPendingEffects", "timing": "turnEnd" },
    { "id": "decay",   "op": "decay" },
    { "id": "faints",  "op": "handleFaints" },
    { "id": "terminal","op": "terminalCheck" }
  ]
}
```

- **流程算子**（`pipelineOps`）是**受控词汇**，每个是代码里的纯函数（`(ctx, stage) => events`）：`dispatchTrigger` / `runPendingEffects` / `wishPhase` / `switchPhase` / `declareActions` / `resolveQueue` / `executeAction` / `damagePhase` / `decay` / `handleFaints` / `terminalCheck` / `emit` / `branch`。
- 好处：**改阶段顺序、增删触发时点、开关阶段**都不用动 `battle.ts`。
- 不做图灵完备脚本：只支持线性阶段 + 受控 `branch`（见 §7）。

### 4.3 `FormulaSpec`（伤害公式 = 数据）

`computeDamage()` 现为硬编码公式；改为**纯数值表达式 AST**：

```json
{
  "version": "1.0.0",
  "inputs": ["power","atk","dfn","typeMult","stab","stageMult","traitMult","weatherMult","extraMult","reduction","hits","balance"],
  "steps": [
    { "let": "effectivePower", "expr": ["mul","power","typeMult","stab","stageMult","traitMult","weatherMult","extraMult"] },
    { "let": "perHit", "expr": ["floor", ["div", ["mul","atk","effectivePower","balance"], "dfn"]] },
    { "let": "damage", "expr": ["floor", ["mul","perHit", ["sub", 1, ["div","reduction",100]], "hits"]] }
  ],
  "output": "damage",
  "breakdown": ["atk","dfn","effectivePower","perHit","stageMult","stab","typeMult","traitMult","weatherMult","extraMult","reduction","hits"]
}
```

- 表达式算子（封闭集）：`add/sub/mul/div/floor/ceil/round/min/max/pow/clamp`，叶子为 `inputs` 名或数字常量。
- `output` / `breakdown` 决定返回与解释面板；求值器是纯函数，安全、可比对。
- 输入量（atk/dfn/typeMult/…）由解释器按既有规则算好后作为变量传入。

### 4.4 `EngineExtension`（指令集可插拔）

```ts
interface EngineExtension {
  id: string;
  triggers?: Record<string, TriggerSpec>;       // 新增触发点
  operators?: Record<string, OperatorSpec>;     // 新增条件算子
  effects?: Record<string, EffectHandler>;      // 新增效果处理器
  pipelineOps?: Record<string, PipelineOp>;     // 新增流程算子
}
```

- `effectHandlers` 取代 `runtime.ts` 的 `switch(effect.type)`；`operators` 取代 `conditions.ts` 的 `switch(op)`；`triggers` 取代 `TriggerName` 联合类型；`pipelineOps` 取代 `step()` 里的内联阶段。
- **内建原语即一个内建扩展**（`engine/builtins.ts` 调 `ext.engine`），保证「扩展路径」永远被走通。
- 扩展是**代码模块**（有类型、可 review、可测试），不是 JSON 脚本。

## 5. 现有代码 → 目标结构（迁移映射）

| 现状 | 现位置 | 目标 |
| --- | --- | --- |
| 回合流程硬编码 | `simulator/battle.ts#step` | `pipeline.json` + `pipelineOps` 注册表 |
| 伤害公式硬编码 | `effects/damage.ts#computeDamage` | `formula.json` + 表达式求值器 |
| 效果分支 `switch` | `mechanisms/runtime.ts#applyStateCommands` | `effectHandlers` 注册表 |
| 条件算子 `switch` | `mechanisms/conditions.ts#matches` | `operators` 注册表 |
| 触发点联合类型 | `mechanisms/types.ts#TriggerName` | `triggers` 注册表（类型由注册表导出） |
| 装配单一 bundle | `data.ts#buildBundle` / `server.ts#getBundle` | `EngineBundle` + `reload` / 沙盒实例 |
| Worker 单次 init | `worker/engine.worker.ts` / `client.ts` | `init(bundle)` + `reload(bundle)`（可隔离草稿） |
| 事件丢 trigger | `simulator/battle.ts#asBattleEvent` | 保留 `trigger`（《引擎工作台》W0） |
| 伤害丢 breakdown | `mechanisms/runtime.ts#applyDamageCommands` | 挂 `data.breakdown`（《引擎工作台》W0） |

## 6. 接口 / 数据契约

- **`buildBundle(raw)` → `EngineBundle`**：读 `data/*.json`（含新 `pipeline.json` / `formula.json`），产出含 `specVersion` / `bundleHash` 的完整定义；`bundleHash = hash(pipeline, formula, mechanisms, extensions manifest)`。
- **`createEngine(bundle)` / `engine.reload(bundle)`**：解释器实例化/热换；沙盒用独立实例，不污染线上。
- **`GET /api/engine/workbench/schema`**：返回注册表（可用 trigger / op / effect 及其字段），UI 不硬编码。
- **校验**：`validate(spec)` 覆盖未知 op/effect、表达式未定义变量、pipeline 引用了未注册 op、`output` 缺失等。
- **回放/试跑契约**：任何记录都带 `{ engineVersion, specVersion, dataVersion, bundleHash }`；加载时不一致要提示。

## 7. 关键决策与风险

- **D1 三层可改性模型**：策略=数据、指令集=可插拔代码、解释器=极简固定。回答「引擎自身能否 JSON 化」：**策略层能，指令集/算法层不能**，但可插拔。
- **D2 表达式用封闭 AST，不用脚本**：无 `eval`、无副作用、算子封闭；条件/效果**语义**仍必须代码实现。
- **D3 pipeline 不做图灵完备**：只线性阶段 + 受控 `branch`；避免失控与安全问题。
- **D4 内建与扩展同接口**：杜绝「内建特例 + 扩展路径」两套逻辑漂移。
- **D5 迁移而非并行**：数据化落地后**删除**旧硬编码（`step` / `computeDamage` 公式体 / `switch`），避免双事实源。
- **D6 确定性钉版本**：`bundleHash` 进回放；试跑用沙盒。
- **风险 R1**：`pipeline` 数据化是**最大改动面**（`step` 耦合了换人、愿力、队列、应对、阵亡等多处），必须一次一阶段迁移 + 逐阶段回归，不能一把梭。
- **风险 R2**：`formula` 数据化后，`calc.ts`（预览/展示侧）必须同口径切到同一 `FormulaSpec`，否则预览与执行分叉。

## 8. 非目标

- 不执行任意代码 / 脚本（数据层无 `Function` / `eval`）。
- 不做图灵完备流程引擎。
- 不改外部图鉴同步、DSH / 站点数据。
- 不改 MCTS 搜索语义（用同一 `EngineBundle` 跑即可，但本稿不重构搜索）。
- 不做多人协作 / 云端定义库。

## 9. 实施分期

| 期 | 内容 | 依赖 | 风险 |
| --- | --- | --- | --- |
| W0 内省补强 | 事件保留 `trigger`、伤害挂 `breakdown`、暴露 `legalActions`（《引擎工作台》W0） | 无 | 低 |
| P1 formula → 数据 | `FormulaSpec` + 表达式求值器；`computeDamage` 改为读 spec；同步 `calc.ts` 口径 | W0 | 中 |
| P2 pipeline → 数据 | `PipelineSpec` + `pipelineOps`；逐阶段从 `step` 迁出 | P1 | 高 |
| P3 指令集注册表 + EngineBundle | `effectHandlers` / `operators` / `triggers` / `pipelineOps` 注册表；内建走 `EngineExtension`；`buildBundle→EngineBundle` + `reload`/沙盒 | P2 | 中 |
| P4 工作台 | 编辑 `mechanisms`/`pipeline`/`formula` + 校验 + 试跑 + 版本库 + `apply`（《引擎工作台》W2/W3） | P3 | 中 |

> 顺序理由：先做**自包含、可单测**的 formula，再动耦合最深的 pipeline；注册表与 EngineBundle 是工作台的前置；UI 最后。

## 10. 待校准

1. `pipelineOps` 粒度（是否把换人/愿力/应对各自成 op，还是合并）。
2. 表达式算子集是否够用（是否需要 `if` / 比较 / 取整变体）。
3. 扩展加载：构建期 manifest，还是运行期动态 `import()`（影响沙盒与版本）。
4. `pipeline`/`formula` 是否随 `data/` 入仓并纳入 `export-static-data`。
5. 沙盒是否需要独立 Worker 池（多草稿并行试跑）。
