## 1. 定位与边界

- **定位**：打开 `/engine` 第一眼是**引擎全景图**——以回合生命周期为骨架，把 695 条机制按触发器挂载成一张全局地图；用户在调试沙盒 / 对战台做了操作后，回来看这张图上**哪些触发器被派发、哪些机制被命中、产生了哪些效果**（点亮）。
- **解决的痛点**：现有 `/engine` 一次只能看一条机制的程序图，无法回答「引擎整体长什么样」「刚才那一局走了哪些路」。
- **边界**：
  - 纯展示 + 数据通道，**不改引擎结算语义**、不改 `mechanisms.json` 结构。
  - 高亮粒度到**触发器 → 机制 → 效果类型**三层；**不做**逐程序节点（read/cmp/分支）点亮——那是《引擎执行图》全量 trace 的领域，collect 模式为性能不记 trace。
  - 不提供图编辑：编辑仍归现有单机制工作台（全景图只下钻）。

## 2. 设计原则

1. **骨架优先**：不平铺 695 条机制（不可读），以固定回合生命周期为轴，机制按触发器折叠分组。
2. **零引擎改动取数据**：`BattleEvent.data` 已带 `trigger` / `mechanismId` / `effectType`（`battle.ts#asBattleEvent`），沙盒 `debugStep` 与对战台 `simulateTurn` 都返回带这些字段的 `log`——点亮所需全部信息已存在。
3. **轨迹跨页面**：对战台在 `/record`、全景图在 `/engine`，轨迹经 `localStorage` 会话存储传递（与 `roco.replays` 同一模式：限额 + 降级）。
4. **复用不重建**：机制列表数据复用 `GET /api/engine/workbench/mechanisms`；下钻复用现有 `WorkbenchView`（`?m=` 深链已存在）；触发器中文名复用 `TRIGGER_VOCABULARY`。

## 3. 全景图骨架（领域模型）

### 3.1 生命周期阶段（静态定义 `lifecycle.ts`，与 `battle.ts#step` 实际派发顺序对齐）

| # | 阶段 | 挂载触发器 | 派发时机（代码锚点） |
| --- | --- | --- | --- |
| 1 | 开局（仅第 1 回合） | `onEntry`（开局在场各一次）、`battleStart` | `step()` 首回合块 |
| 2 | 回合开始 | `turnStart`（按侧）+ 延迟效果（`timing: turnStart`） | `step()` ① 前 |
| 3 | 愿力 | 无触发器（愿力冲击为内置动作） | `step()` ① |
| 4 | 换人 | `beforeSwitch` → `onEntry` → `afterSwitch`（含入场继承队列） | `doSwitch` / `enterField` |
| 5 | 行动宣告与排序 | `actionDeclared`（按侧行动侧） | `step()` ③ 入队前 |
| 6 | 行动结算 | `beforeAction` → `skillUsed`（技能）→ `actionResolved` | `step()` ③ 队列逐条 |
| 7 | 伤害结算 | `beforeDamage` → `onHit`（印记携带者）→ `afterDamage` | `executeSkill` |
| 8 | 回合结束 | `turnEnd`（按侧）+ 延迟效果（`timing: turnEnd`）→ 环境衰减 | `step()` ④ |
| 9 | 阵亡 | `beforeDeath` → `afterDeath` | `handleFaints` |
| 10 | 实体级联（随时） | `statusApplied` / `statusReached` / `markApplied` / `markReached` / `buffGained` / `debuffGained` | `runtime#applyStateCommands` 级联 |
| 11 | 被动查询（随时） | `passive` | `ruleModifiers` / 能耗等按需读取，**不计入回合流** |

### 3.2 未接线触发器（灰态展示）

词表存在但模拟器**当前不派发**的触发器在骨架上标「未接线」灰态，避免用户误以为它们会触发：

`beforeActionOrder`、`actionOrderResolved`、`beforeEffect`、`afterEffect`、`battleEnd`、`weatherChanged`、`skillCooldownReduced`

（事实依据：全仓 `trigger: "<name>"` 派发点检索仅命中 types / vocabulary 定义，无运行时调用。）

### 3.3 机制分组计数

挂载机制数来自 `GET /api/engine/workbench/mechanisms` 按 `trigger` 分组（实测分布）：`beforeAction` 288、`beforeDamage` 53、`battleStart` 40、`onEntry` 21、`turnStart` 15、`turnEnd` 14、`actionDeclared` 11、`skillUsed` 8、`actionResolved` 6、`afterDamage` 5、`afterDeath` 4、`statusApplied` 4、`debuffGained` 3、`buffGained` 3、`onHit` 2、`passive` 1、`statusReached` 1、`afterSwitch` 1；其余触发器 0 条。

## 4. 运行时轨迹（点亮）

### 4.1 轨迹模型

```ts
/** 一次「用户操作 → 引擎响应」的聚合（纯函数产出，可单测）。 */
interface AtlasStep {
  turn: number;                       // 事件所属回合（state.turn，由写入方标注）
  actions: { side: Side; kind: ActionKind; skillId?: string; benchId?: string }[]; // 用户做了哪些操作
  fired: {                            // 走了哪些节点（按事件首次出现序）
    trigger: string;                  // data.trigger（无 trigger 的引擎原生事件跳过）
    mechanisms: string[];             // 该触发器下命中的 mechanismId（去重）
    effects: string[];                // 该触发器下出现的 effectType（去重）
  }[];
}

/** localStorage 会话轨迹（键 `roco.atlasTrace`）。 */
interface AtlasTrace {
  source: "debug" | "board";          // 来自调试沙盒 / 对战台
  updatedAt: number;
  steps: AtlasStep[];                 // 限额：最近 50 步（超限头淘汰）
}
```

聚合规则（`modules/atlas/collect.ts`，纯函数）：

- 遍历 `log`（`BattleEvent[]`），跳过 `data.trigger` 缺失的事件（换人 / 愿力 / 阵亡提示等引擎原生事件——它们由阶段 4 / 9 的**触发器事件**间接体现）。
- 按 `data.trigger` 归桶、保持**首次出现序**；桶内 `mechanismId` / `effectType` 去重。
- 同一触发器多桶（多侧 / 多次派发）**合并为一桶**，机制命中累计在 `steps` 各条里——点亮看「本步该触发器命中过哪些机制」，次数显示在机制徽章上（聚合时计数 `Record<string, number>`，接口里 `mechanisms` 携带 `{ id, count }`）。

### 4.2 写入点（2 处，均为调用侧埋点，引擎无改动）

| 写入点 | 位置 | 捕获内容 |
| --- | --- | --- |
| 调试沙盒 | `debug-view.tsx#step()` 成功后 | `actions`（`playerIndex` / `enemyIndex` 对应的合法行动）+ `result.log` |
| 对战台 | `board.tsx` 各 `simulate/step` / `forced-switch` 成功后 | 本回合双方所选动作 + `res.log` |

写入 = 聚合 + 限额写 `localStorage["roco.atlasTrace"]`（超配额降级只保留最近 5 步，同 `replays/storage.ts` 模式）。

### 4.3 点亮展示

- **触发器节点**：本轨迹有该触发器事件 → 主色描边 + 命中次数徽章；0 次不亮。
- **机制卡片**（点触发器展开 / 或右侧列表）：命中 ≥1 次 → 高亮 + 次数；点卡片下钻现有单机制程序图（`?m=<id>`）。
- **效果类型**：机制卡片下挂小标签（如 `dealDamage`），命中过才显示。
- **轨迹条**（页面顶部）：`来源（沙盒/对战台）· N 步 · 回合 X · 操作：我方技能「猛烈撞击」/ 敌方换人` + 「清除轨迹」按钮；无轨迹时显示引导文案（「去调试沙盒单步，或打一局对战，回来点亮此图」）。
- 点亮**只反映最近一次来源的轨迹**（覆盖写，不做多局叠加——第一期从简）。

## 6. 关键决策

1. **骨架用静态表而非从代码生成**：`lifecycle.ts` 与 `step()` 手工对齐（代码注释锚点），换取零依赖与可读性；漂移风险由单测断言「骨架触发器 ⊆ 词表、挂载计数 = 分组结果」兜底。
2. **轨迹走 localStorage 而非全局状态**：对战台 / 沙盒 / 全景图是三个路由，跨页传递只有 storage 可靠；且与回放同一套心智。
3. **不点亮「派发了但无命中」的触发器**：事件流只在有事件时携带 trigger，未命中即无事件——骨架上区分「已派发未命中」需要引擎在 dispatch 层加探针，**超第一期边界**（列入非目标）。
4. **粒度止步于机制**：效果类型作为机制卡片的附属标签展示，不再下钻到 `effects[j]`——现有程序图已有该视角。
5. **版本**：纯 UI + 数据通道，**bump minor `0.46.0`**；`ENGINE_VERSION` 不动（无新触发器 / 效果命令 / 结算阶段）。

## 7. 非目标

- 逐程序节点（read/cmp/分支）点亮与全量 trace 采集（属《引擎执行图》G 系列后续）。
- 「已派发但 0 命中」的触发器点亮（需 dispatch 探针）。
- 多局轨迹叠加 / 历史轨迹列表（回放接入留 P4）。
- 全景图内编辑机制（编辑归现有工作台）。
- 移动端流程图的深度优化（先满足 `min-[860px]`，窄屏节点改纵向堆叠 + `overflow-x`）。

### 修订 2026-10-04（UI 返工：表格感 → React Flow 节点-连线图，并补全至 29 个触发点）

- 阶段 = **方块节点**（含序号、条件标签、机制数、触发器小卡）；执行先后 = **带箭头的平滑连线**。
- 蛇形三列主序列（1→2→3 下行 · 3→4 横接 · 4→5→6 上行 · 6→7 横接 · 7→8→9 下行 → 10 对局结束）。
- **覆盖引擎全部 29 个触发器**（此前只画主序列 15 个）：
  - 主序列 15（10 个阶段节点）；
  - 旁路 7（实体级联 6 + 被动查询 1）入图，由「伤害结算」虚线分支「效果后 · 随时派发 / 按需读取」；
  - 未接线 6（行动排序前/后、效果执行前/后、天气变化、冷却减少）单列灰虚线节点（`battleEnd` 已作主序列收尾节点「对局结束」）。
- 阵亡 → 回合开始 为「下一回合（回环）」连线；阵亡 → 对局结束 为「任一方全灭」。
- **可缩放 / 平移**（滚轮缩放、拖拽平移、控制条 fitView），适配宽窄屏。
- 点亮：阶段内触发器命中 → 节点主色描边；首尾都命中的连线描主色并流动。
